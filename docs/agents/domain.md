# Domain 文档

工程类技能在探索本仓库时应如何消费领域文档。

## 探索前先读

- 根目录 **`GLOSSARY.md`**
- 若存在根目录 **`GLOSSARY-MAP.md`**：它指向每个上下文各自的 `GLOSSARY.md`，读与当前议题相关的那些
- **`docs/adr/`**：读涉及待改动领域的 ADR。多上下文仓库还要看 `src/<context>/docs/adr/` 下的上下文级决策

这些文件不存在就**静默继续**：不要指出缺失，也不要主动建议先建。`/domain-modeling` 技能（经 `/grill-with-docs` 与 `/improve-codebase-architecture` 到达）会在术语或决策真正落定时才惰性创建。

## 文件布局

本仓库为**单上下文**：

```text
/
├── GLOSSARY.md
├── docs/
│   ├── adr/
│   │   ├── 0001-事件溯源订单.md
│   │   └── 0002-写模型使用-postgres.md
│   └── agents/          ← 本目录：技能配置
└── <电机|通信协议|控制算法|石山代码>/   ← 现有内容分类
```

## 使用术语表中的词汇

输出里命名领域概念时（issue 标题、重构提案、假设、测试名），使用 `GLOSSARY.md` 定义的说法，不要漂移到术语表明确回避的同义词。

需要的概念还没进术语表，本身就是信号：要么你在发明项目不用的语言（重新考虑），要么确实存在缺口（记下来交给 `/domain-modeling`）。

## 标出 ADR 冲突

若输出与既有 ADR 相矛盾，明确标出而不是悄悄覆盖：

> _与 ADR-0007（事件溯源订单）冲突，但值得重开，因为…_
